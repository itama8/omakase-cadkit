# 2026-10-25 / s12 — Hatch text boxes stay clear

Outcome: O5 · State: partial
Source: this change · Environment: Linux x64, Node 25.8, .NET 8, headless Chromium

## Result

Superseded by [s14](2026-10-25-s14.md): user review found that subtracting the
text box cut gaps into the frame. The checks here incorrectly required those gaps.

Boxed labels no longer turn into pale filled rectangles. The reported real DWG hatch
`2E65` has two ordinary loops and an overlapping text-box loop. The reader previously
lost the boundary flags, so even-odd filling filled the label interior back in.
The corrected viewer shows readable lettering inside a hollow border. SVG export and
selection highlighting preserve the same exclusion. CAD font substitution remains.
This is a focused fidelity fix, not general AutoCAD rendering equivalence.

## Changes and decisions

- Sidecar separates `Textbox`/`TextIsland` boundaries from ordinary parity loops;
  text boxes always subtract, even across another hole or another text box.
- Payload schema 4 adds optional exclusion loops to fill primitives. Types and the
  store's accepted schema change together. Cached drawing payload JSON was removed;
  recent files and viewer preferences were retained. The local server was restarted.
- Canvas clips each text exclusion separately, without painting over underlying
  geometry. Independent fill primitives no longer share an even-odd batch, which
  also prevents overlapping hatches from cancelling each other. Selection uses
  the same clipping helper. SVG uses a luminance mask with independent black boxes.
- `fixtures/hatch_text.dxf` is generated from synthetic geometry. It exercises nested
  islands, overlapping text boxes crossing a border, underlying linework, independent
  overlapping fills, and a rotated/scaled block. `test/hatch.test.ts` checks payload
  geometry and SVG masks; `scripts/hatch-check.js` checks actual canvas pixels.
- Hatch-style expansion was left outside this fix. A temporary raw-reader probe
  showed ACadSharp 3.8 reads DXF hatch styles as Normal even when ezdxf reads distinct
  source styles. No broader style-support claim is made here.
